interviewScript: "When approaching a system design interview, I always start by clarifying requirements and estimating scale. My go-to architecture for high scale relies on horizontal scaling behind a Load Balancer. I heavily utilize caching (Redis/Memcached) to protect the database from read-heavy operations. If a process is slow or asynchronous, I decouple it using a message queue (like Kafka or SQS) to prevent blocking the main request cycle. Finally, I always address the CAP theorem—in distributed systems, network partitions will happen, so we must choose between strict Consistency (like banking) or high Availability (like a social feed)."
pitfalls:
  - "Designing a complex microservice architecture for an MVP that could easily be a monolith."
  - "Forgetting to identify single points of failure (SPOF) in the design."
  - "Applying a 'silver bullet' technology (e.g., Kafka) without justifying why it's needed over a simpler solution (e.g., SQS or Redis Pub/Sub)."
  - "Ignoring rate limiting and API gateway security for public-facing services."

## Deep Dive: The CAP Theorem

The CAP theorem states that a distributed data store can only simultaneously provide two of the following three guarantees: Consistency, Availability, and Partition Tolerance.
